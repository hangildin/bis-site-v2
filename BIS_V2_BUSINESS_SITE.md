## Как создать отдельный реально работающий сайт, сохранив основной

В текущем подключении GitHub **нет действия «создать новый репозиторий» или «изменить Pages»**. Поэтому не могу выдавать ещё несуществующий URL `bis-site-v2` за опубликованный. Для отдельного GitHub Pages потребуется один раз создать второй репозиторий.

**Настройка собственником на GitHub (основной bis-site не трогать):**

1. Открыть https://github.com/new/import (GitHub Importer).
2. Источник: `https://github.com/hangildin/bis-site.git`; владелец `hangildin`, название **`bis-site-v2`**, видимость **Public**. Начать импорт репозитория. После импорта в новом репозитории должны присутствовать обе ветки, включая `bis-v2-development`. Если интерфейс не импортирует GitHub-источник, сделать зеркальный перенос через Git; к основному сайту это не относится.
3. В **новом** репозитории `bis-site-v2` открыть **Settings → General → Default branch** и переключить на **`bis-v2-development`**. В исходном `bis-site` ничего не переключать.
4. В **новом** репозитории выбрать **Settings → Pages → Build and deployment → Source: GitHub Actions**.
5. В **новом** репозитории открыть **Actions → BIS V2 commercial site deployment → Run workflow**, ветка `bis-v2-development`. При необходимости включить GitHub Actions для импортированного кода.
6. Сборка автоматически проверяет 25 страниц, переписывает sitemap/canonical и загружает сайт. Проверить опубликованный адрес на вкладке Pages.

**Ожидаемый адрес, не утверждение о существовании:** `https://hangildin.github.io/bis-site-v2/`.

**Безопасность:** файл `.github/workflows/bis-v2-deploy-separate.yml` содержит защиту `if: github.repository == 'hangildin/bis-site-v2'`. В исходном `hangildin/bis-site` job **пропускается** и не может заменить существующий сайт. Он работает только в названном новом репозитории.

Официальные инструкции GitHub:
- Импорт: https://docs.github.com/en/migrations/importing-source-code/using-github-importer/importing-a-repository-with-github-importer
- Публикация через GitHub Actions: https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site
- Запуск workflow вручную: https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow

## Качество: объективные проверки, а не обещание 10/10

- `.github/scripts/check_services.py` — навигация коммерческих услуг.
- `.github/scripts/check_content_v2.py` — контакты, факты, запрет недостоверного стажа и спорных цифр.
- `.github/scripts/check_portfolio_v2.py` — семь проверенных кейсов и связи.
- `.github/scripts/check_journal_v2.py` — восемь статей, Article schema, ссылки и содержательность.
- `.github/scripts/check_technical_seo_v2.py` — метаданные и карта сайта из 25 страниц.
- `scripts/check_release.py` — реальная публичная сборка: отсутствие старых canonical, sitemap, ссылки, картинки, 64 ключа и 15 объявлений.
- `scripts/visual_smoke_v2.mjs` — настоящий браузер Chrome по 25 страницам в пяти размерах.

**10/10 не ставить автоматически.** Полный балл возможен только после реального выпуска на отдельном адресе и проверки мобильной скорости, UX и первичных данных поискового трафика. До этого результат нужно называть готовностью исходников и содержимого, а не доказанным коммерческим успехом.

## Следующий порядок действий после публикации

1. Проверить реальный URL и HTTPS, 25 страниц, номера телефонов и клики по мессенджерам.
2. Яндекс Вебмастер: подтвердить право на отдельный сайт, отправить sitemap и проверить индексирование.
3. Яндекс Метрика: настроить счётчик и цели звонка/e-mail/Telegram. Учитывать требования к уведомлениям о cookies и сбору аналитики.
4. Подготовить рекламный кабинет/реквизиты рекламодателя; получить фактический прогноз Директа и согласовать бюджет.
5. Выгрузить объявления с UTM из `scripts/render_direct_ads.py`, проверить целевые страницы и модерацию; **только после отдельного подтверждения** запустить кампании.
6. Отслеживать фактические поисковые запросы, стоимость целевых обращений, а не только клики и CTR.
